# 设计说明

这份文档讲清楚三件事：数据从哪来、为什么只有一个钩子、请求文件怎么和对话对上。
文档假设读者不了解这个项目的历史，只知道它是一个本地看板。

## 一、项目做什么

页面上只有两种数据：

1. **Pi 的会话文件（JSONL）**：Pi 每次对话都会往 `~/.pi/agent/sessions/` 下的文件里追加条目，
   一个文件就是一次会话。看板把这些条目渲染成时间线。
2. **provider 请求正文**：每次模型请求实际发出去的请求体。探针把它原样存成文件，
   放在 iCloud 的一个文件夹里。看板不读这些正文，只在对话里显示对应文件的名字。

除此之外的一切——数据库、实时推送、探针状态、保留期、设置页——都没有了。

## 二、为什么不用数据库

会话文件本身就是结构化数据，而且就是唯一真相源。建一个库意味着要把文件里的东西
再抄一份进 SQLite，于是要处理两份数据不一致的问题（文件被改写、库里的旧行、
增量与全量的对账），还要维护 schema、迁移、保留期。

不建库的代价是每次读会话都要重新解析文件。一个 50 MB 的会话文件解析要 0.4 秒左右，
所以解析结果按「路径 + 修改时间 + 大小」缓存在内存里，最近 3 个会话。
文件没变时重复打开是瞬时的；文件变了就重新解析，缓存里最多留一份旧结果。

页面上一次只给 20 个 Turn，「加载更早」再问服务端要更早的一段，
所以浏览器不会为了一个大会话一次拉走几 MB 的 JSON。

## 三、为什么探针只留一个钩子

Pi 的扩展能订阅十几个事件：会话生命周期、agent 起止、turn 起止、工具起止、
模型切换、思考等级切换、压缩、请求与响应……

其中大部分信息会话文件里已经有了，而且是更完整的那一份：

| 原来订阅的事件 | 文件里对应的 |
|:--|:--|
| `session_info_changed` | `session_info` 条目 |
| `model_select` | `model_change` 条目 |
| `thinking_level_select` | `thinking_level_change` 条目 |
| `session_tree` | 条目的 `parentId` 构成的树 |
| `session_compact` | `compaction` 条目 |
| `agent_end` | 助手条目的数量 |
| `turn_start` / `turn_end` | 助手消息里的 `stopReason`、`thinkingLevel`、`usage`、`cost` |
| `tool_execution_start` / `tool_execution_end` | 助手消息里的工具调用 + toolResult 条目里的 `isError` 与 `durationMs` |

只有两样东西文件里没有：

- **请求 payload**：文件里存的是「对话」，不是「这次请求实际发出去的那份结构」
  （系统提示、工具定义、缓存控制都在里面）。
- **响应状态码与 headers**：文件里没有原始响应头。

请求正文是需求明确要的东西，所以留 `before_provider_request`。
响应状态码与 headers 这次没要（需求里只有「原始请求正文」），所以没有订阅
`after_provider_response`。

代价是丢掉了几样东西，说清楚免得以后困惑：

- **运行状态**：原来「进行中 / 空闲 / 已结束」来自探针的 `agent_start` / `agent_settled`。
  现在看板不知道此刻有没有会话在跑，页面上不再显示状态。
- **用户是否中断**（`aborted`）：文件里没有这个信号。
- **压缩失败的原因**：文件里只有成功的 `compaction` 条目。
- **精确的 Turn 边界**：Turn 现在按「用户消息」切，一条助手消息算一个模型 Turn，
  开始时间用上一条条目的时间近似。

## 四、请求文件怎么和对话对上

请求与响应是串行的：Pi 的请求一个接一个发，一个响应回来才会有下一个。
所以一条助手消息对应一次请求。

对号规则：**时间不晚于这条助手消息、且还没有被用掉的最后一个请求文件**。

- 文件名里的时间戳是写文件的时间（也就是请求发出的时刻），
  助手消息的时间戳是响应回来的时刻，所以请求一定排在前面。
- 失败重试会让同一个助手消息前面有两个请求文件：规则会把后一个（真正成功的那次）
  对上这条消息，先前那个自然落在外面。
- 探针装得晚时，会话开头的一部分助手消息没有对应的请求文件：它们显示为空，
  不编造。

用不上号的请求文件数记在 `unmatched_requests` 里。

## 五、空间占用

会话文件本身不大：本机 74 个会话文件合计 131 MB。

**请求正文会很大，而且增长很快。** 一份请求体里几乎全是 `messages`——
每次请求都把到目前为止的整段对话重新发一遍。一个 1913 次请求的会话，
请求正文加起来 29 GB。存储量随对话长度按平方增长。

所以：

- 请求正文放在 iCloud 而不是本机磁盘，是为了不占本机空间；
- 想清理就直接在 Finder 里删那个文件夹里的文件，不影响看板（看板本来就不读它们）；
- 如果以后嫌它太大，唯一的办法是改变存法：只存相对上一次请求新增的消息，
  或者按内容分块去重。这需要改探针的写法，本版没有做。

## 六、探针的约束

- 只读：不调用 Pi 的任何写入接口，不改 `event` 上的对象，不返回替换值。
- 不发网络请求：探针不连看板，写完文件就结束。
- 写文件失败不影响 Pi：异常只写一行 stderr 日志，绝不抛给 Pi。
- 写文件先写临时文件再改名：iCloud 同步半个文件比同步一个坏文件麻烦。
